# Ограничения запросов и обновление контакта

Причина сбоя UI-03 установлена по трассировке: PATCH контакта получил HTTP 429 до вызова БД. Это не занятое соединение и не сохранение старого значения в БД. API уже отдавал Cache-Control: no-store. Полный E2E-набор исчерпывал общий лимит 600 запросов/минуту с одного IP; вход имел отдельный лимит 30.

Новая политика на один процесс приложения:

| Ограничение              | По умолчанию               | Настройка               |
| ------------------------ | -------------------------- | ----------------------- |
| Авторизованный сотрудник | 3000 запросов/минуту на ID | API_RATE_LIMIT_PER_USER |
| Защитный общий API по IP | 6000 запросов/минуту       | API_RATE_LIMIT_PER_IP   |
| Неавторизованный API     | 600 запросов/минуту на IP  | Не меняется             |
| Вход                     | 30 запросов/минуту на IP   | Не меняется             |

Укажите настройки в .env и перезапустите приложение. Допустимы целые значения 1–100000, ноль не отключает защиту. Без настроек используются значения таблицы. У одного сотрудника общий бюджет на все его действующие сессии; токен с поддельной подписью не создаёт отдельный персональный бюджет. Проверка активности и прав в AuthGuard сохранена. Общий лимит IP действует и на авторизованных сотрудников.

При 429 сервер сообщает Retry-After и retryAfter в JSON. Текст ошибки указывает оставшиеся секунды. Нет автоматического повторения мутаций: пользователь исправляет/повторяет сохранение сам. Форма сохраняет введённые данные при отказе.

После успешного изменения запись в карточке заменяется подтверждённым ответом БД, затем перечитывается вся карточка. Более ранний ответ GET не может перезаписать более свежий. Ошибка последующего перечитывания показывается как «Запись сохранена, но не удалось обновить данные», без ложного сообщения об отказе сохранения. Клиентские API-запросы используют cache: no-store.

Security review: счётчик сотрудника создаётся только после криптографической проверки подписанной сессии; произвольный bearer и X-Forwarded-For не дают обхода. Источник IP — socket.remoteAddress. За reverse proxy несколько сотрудников могут делить IP прокси; настройка доверенных прокси не менялась. Счётчики ограничены по памяти и не вытесняют активные окна ради нового ключа. Это не распределённый rate limiter: при нескольких репликах бюджеты независимы. Для горизонтального масштабирования нужен общий счётчик или лимит на gateway.

Workflow: Developer — исправлены политика и обновление; Security — проверены подпись, общий IP, anonymous/auth и сохранение ACL; QA — unit и HTTP integration, отказ/повторное сохранение и проверка БД на desktop/mobile; Release — отдельная ветка, без выкладки. Миграция БД не нужна. Откат — предыдущая сборка и удаление новых env-настроек; данные контактов не удаляются.

Фактический полный прогон 5 октября 2026: `npm run check` — 302 успешных теста, 2 пропущены, 7 эксплуатационных проверок и сборка успешны. `npm run test:e2e` — 50/50 desktop/mobile; ранее падавшие UI-03 и UI-04 прошли в полном наборе. HTTP integration дополнительно проверяет независимые бюджеты пользователей с одного IP, поддельную подпись (401), заблокированного пользователя (403), общий лимит IP, Retry-After и неизменный лимит входа.
