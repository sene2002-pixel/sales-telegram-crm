# Развёртывание и эксплуатация

## Production

1. Создайте бота в BotFather. В `.env` заполните `BOT_TOKEN`, числовой `BOOTSTRAP_ADMIN_TELEGRAM_ID`, `OPENAI_API_KEY`, `PUBLIC_URL=https://crm.example.com`.
2. Сгенерируйте отдельные `SESSION_SECRET`, `TELEGRAM_WEBHOOK_SECRET`, `POSTGRES_PASSWORD`: `openssl rand -hex 32`. Не используйте одну строку для разных секретов. Hex-пароль подходит для PostgreSQL URL без дополнительного кодирования.
3. Установите `NODE_ENV=production`, `DEV_AUTH=false`, `HOST=0.0.0.0`. В Compose адрес PostgreSQL формируется автоматически. При запуске без Compose задайте `DATABASE_URL` самостоятельно.
4. Подготовьте каталог вложений с правом записи для UID 1000 контейнера: `mkdir -p data/files`, на Linux `sudo chown 1000:1000 data/files`. Существующие данные сохраняйте.
5. Запустите `docker compose up -d --build`. PostgreSQL не публикует свой порт; HTTP API доступен только на loopback порту 3000 хоста.
6. Настройте HTTPS reverse proxy на 127.0.0.1:3000. Передавайте весь `/api` и `/` без изменения путей. Ограничьте размер тела 11 МБ; ограничьте запросы на gateway. В этой версии приложение не доверяет X-Forwarded-For для авторизации.
7. Выполните `docker compose exec app node dist/server/setup-telegram.js`. Скрипт регистрирует команды, кнопку меню и webhook; старые необработанные updates не удаляет.
8. Откройте `/crm` в личном чате бота под bootstrap ID. Добавьте остальных сотрудников на экране команды. Токен бота и ключ ИИ никогда не вводятся в клиентский интерфейс.

`PUBLIC_URL` задавайте без завершающего `/`. Модели распознавания и извлечения можно менять через `TRANSCRIPTION_MODEL` и `EXTRACTION_MODEL`, проверив поддержку транскрипции/Structured Outputs выбранной моделью.

## Поддержка Pico в Telegram Stars

Приём звёзд по умолчанию выключен. Перед включением владелец публикует условия добровольной поддержки по версионированному HTTPS-адресу и назначает ответственного за обращения. Задайте этот адрес в `PICO_STARS_TERMS_URL`, Telegram-username ответственного в `PICO_STARS_SUPPORT_USERNAME` и `PICO_STARS_ENABLED=true`. При изменении условий опубликуйте новую версию по другому адресу. Сервер сверяет адрес при создании счёта и сохраняет принятую версию. [Чек-лист Telegram](https://core.telegram.org/bots/payments-stars#live-checklist)

После сборки и применения настроек выполните `node dist/server/setup-telegram.js` в нужном окружении. Через `getWebhookInfo` проверьте адрес webhook, подписки на `message` и `pre_checkout_query` и ошибки доставки. Проверьте `/api/health`. Изменения `.env` в Compose применяйте через `docker compose up -d --build app`.

**Проверка в Telegram Test Environment**

1. Создайте отдельного пользователя и бота через BotFather в тестовом клиенте Telegram. Поднимите отдельный экземпляр CRM с собственной базой, доменом, каталогом данных, секретом сессий и секретом webhook. На тестовом экземпляре задайте `TELEGRAM_API_ENVIRONMENT=test` и исходный токен тестового бота. Рабочая установка использует `production` (значение по умолчанию). Настройка распространяется на все методы Bot API, загрузки и скачивания файлов. [Настройка тестовой среды Telegram](https://core.telegram.org/bots/features#dedicated-test-environment)
2. Настройте webhook тестового бота. Откройте Mini App в его личном чате, проверьте сумму, ссылку на условия и подтверждение ознакомления. Отмените один счёт до начала оплаты. Затем оплатите новый счёт тестовыми Stars, прервите WebView и проверьте результат после повторного открытия. Сумма должна совпасть в квитанции Telegram и CRM.
3. Для проверки возврата на этом же стенде используйте `refundStarPayment` для тестового платежа. Сверьте результат в Telegram и CRM после доставки события возврата. Отдельно проверьте доступность `/paysupport` с чеком и без него. [Возврат Stars](https://core.telegram.org/bots/api#refundstarpayment)

**Помощь при незавершённом платеже**

Пользователь может отменить счёт до того, как Telegram запросил разрешение на оплату. После разрешения бронь хранится до получения достоверного результата. При обращении через `/paysupport` уточните номер счёта, время и сумму в Stars. Пользователь может приложить чек, если получил его.

В экземпляре CRM нужного бота запустите `npm run telegram:reconcile-stars -- <invoice-id>` после серверной сборки. Команда сверяет запись `pico_star_invoices` с историей `getStarTransactions`. Для входящей оплаты сопоставляются плательщик, сумма, payload счёта и идентификатор транзакции. Для возврата учитывается также направление операции. Telegram использует один идентификатор для покупки и её возврата. Разбор проводит ответственный с доступом к платёжным записям. По умолчанию команда просматривает до 100 страниц по 100 операций. Если история длиннее, повторите со значением `--max-pages N`, достаточным для полной сверки. При неполном просмотре статус счёта сохраняется. [История операций бота](https://core.telegram.org/bots/api#getstartransactions) · [Поля транзакции](https://core.telegram.org/bots/api#startransaction)

Если сверка установила оплату или возврат, ответственный может повторить команду с `--apply` для записи подтверждённого результата в CRM. Деньги эта команда не перемещает. При неполной истории, расхождении реквизитов или отсутствии записи сохраните бронь, проверьте очередь и ошибки webhook, затем повторите сверку. Истечение времени само по себе не подтверждает отмену. Перед согласованным возвратом проверьте историю возвратов и исходный идентификатор списания.

**Выкладка и откат**

Перед миграцией сделайте резервную копию по инструкции ниже. После выкладки проверьте health, чтение старого счёта и обработку событий об уже начавшихся платежах. Для остановки новых оплат установите `PICO_STARS_ENABLED=false` и примените конфигурацию, сохранив поддержку и доставку webhook. Во время отката оставьте таблицу счетов и добавленные поля на месте. Если возвращаете старую версию обработчика, держите приём выключенным и сверьте операции за всё окно отката до повторного включения.

## Приёмочный сценарий с реальными сервисами

- Авторизоваться в Telegram под администратором и двумя менеджерами.
- Отправить голосовое с компанией, контактом и задачей на завтра; дождаться review.
- Проверить транскрипцию и даты, исправить поле, подтвердить; открыть карточку и календарь.
- Дважды нажать подтверждение: задача должна остаться одна.
- Передать компанию второму менеджеру; первому доступ закрыт, автор старого взаимодействия сохранён.
- Перезапустить приложение: записи и вложение сохраняются.
- Отключить ключ ИИ в тестовом окружении: отчёт показывает ошибку; после восстановления конфигурации ручной retry работает.
- Проверить мобильные Telegram на iOS/Android, safe areas, прокрутку, клавиатуру и скачивание вложений.

## Диагностика

Для подробного разбора голосового запроса и генерации письма доступна [временная трассировка только в БД](DIAGNOSTICS.md). Настройка `DIAGNOSTIC_LOG_UNTIL` задаёт момент автоматического отключения; по умолчанию режим выключен.

`GET /api/health` проверяет доступность SQL. `docker compose logs --tail=100 app` показывает структурированные события запуска, ошибок обработки и доставки. Секреты и полный текст диктовки не выводятся в логи. При исчерпании пяти попыток outbox-сообщение остаётся в БД с `attempts=5`; исследуйте доступность бота и повторите доставку административно после устранения причины.

Пример диагностических запросов (в защищённой сессии DBA):

```sql
SELECT status, count(*) FROM reports GROUP BY status;
SELECT id, attempts FROM outbox WHERE NOT sent AND attempts >= 5;
```

Настройте внешние проверки health, дискового пространства, количества failed reports и неотправленных уведомлений. Масштабирование worker выполняйте только с обычным PostgreSQL. Встроенная БД — локальный режим.

## Резервное копирование

Python-скрипт использует стандартную библиотеку из `.venv` и команды Docker Compose. Он отказывается работать, если app запущен, чтобы SQL и вложения были согласованы.

```sh
docker compose stop app
.venv/bin/python scripts/backup.py backup --output backups/crm-2026-09-15.tar.gz
docker compose start app
```

В каталоге `backups/` CRM хранит три последние полные копии базы и вложений. При создании новой копии скрипт сохраняет её и две проверенные предыдущие с самым свежим временем изменения файла. Если запись не удалась, предыдущие копии сохраняются. Для ручного применения того же лимита к существующим архивам при работающем приложении выполните из каталога проекта:

```sh
.venv/bin/python scripts/backup.py prune
```

На Windows используйте `py -3 scripts/backup.py prune`. Ротация действует только в штатном каталоге `backups/` этого проекта.

Архив содержит SQL и файлы. Храните зашифрованную копию вне сервера с ограниченным доступом. Секреты `.env` в архив не попадают; храните их отдельно. Содержимое CRM требует согласованного срока хранения и доступов команды.

Восстановление выполняйте сначала в отдельной тестовой установке. Оно заменяет содержимое CRM-базы; нужен явный флаг:

```sh
docker compose stop app
.venv/bin/python scripts/backup.py restore --input backups/crm-2026-09-15.tar.gz --confirm-restore
docker compose start app
```

После восстановления проверьте health, число компаний, историю, вход менеджера и скачивание контрольного файла. SQL восстанавливается в одной транзакции. Если распаковка вложений завершилась ошибкой, оставьте app остановленным и повторите восстановление. Для Linux восстановите владельца `data/files` (UID 1000).

Для локального PGlite: остановите Node-процесс и копируйте весь `data/` вместе. Скрипт Docker-backup не предназначен для встроенного режима.
