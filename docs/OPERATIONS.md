# Развёртывание и эксплуатация

## Production

1. Создайте бота в BotFather. В `.env` заполните `BOT_TOKEN`, числовой `BOOTSTRAP_ADMIN_TELEGRAM_ID`, `OPENAI_API_KEY`, `PUBLIC_URL=https://crm.example.com`.
2. Сгенерируйте отдельные `SESSION_SECRET`, `TELEGRAM_WEBHOOK_SECRET`, `POSTGRES_PASSWORD`: `openssl rand -hex 32`. Не используйте одну строку для разных секретов. Hex-пароль подходит для PostgreSQL URL без дополнительного кодирования.
3. Установите `NODE_ENV=production`, `DEV_AUTH=false`, `HOST=0.0.0.0`. В Compose адрес PostgreSQL формируется автоматически. При запуске без Compose задайте `DATABASE_URL` самостоятельно.
4. Подготовьте каталог вложений с правом записи для UID 1000 контейнера: `mkdir -p data/files`, на Linux `sudo chown 1000:1000 data/files`. Существующие данные сохраняйте.
5. Запустите `docker compose up -d --build`. PostgreSQL не публикует свой порт; HTTP API доступен только на loopback порту 3000 хоста.
6. Настройте HTTPS reverse proxy на 127.0.0.1:3000. Передавайте весь `/api` и `/` без изменения путей. Ограничьте размер тела 11 МБ; ограничьте запросы на gateway. В этой версии приложение не доверяет X-Forwarded-For для авторизации.
7. Выполните `docker compose exec app node dist/server/setup-telegram.js`. Скрипт регистрирует команды, кнопку меню и webhook; старые необработанные updates не удаляет.
8. Откройте `/crm` в личном чате бота под bootstrap ID. Добавьте остальных сотрудников на экране команды. Токен бота и ключ ИИ никогда не вводятся в клиентский интерфейс.

`PUBLIC_URL` задавайте без завершающего `/`. Модели распознавания и извлечения можно менять через `TRANSCRIPTION_MODEL` и `EXTRACTION_MODEL`, проверив поддержку транскрипции/Structured Outputs выбранной моделью.

## Приёмочный сценарий с реальными сервисами

- Авторизоваться в Telegram под администратором и двумя менеджерами.
- Отправить голосовое с компанией, контактом и задачей на завтра; дождаться review.
- Проверить транскрипцию и даты, исправить поле, подтвердить; открыть карточку и календарь.
- Дважды нажать подтверждение: задача должна остаться одна.
- Передать компанию второму менеджеру; первому доступ закрыт, автор старого взаимодействия сохранён.
- Перезапустить приложение: записи и вложение сохраняются.
- Отключить ключ ИИ в тестовом окружении: отчёт показывает ошибку; после восстановления конфигурации ручной retry работает.
- Проверить мобильные Telegram на iOS/Android, safe areas, прокрутку, клавиатуру и скачивание вложений.

## Диагностика

`GET /api/health` проверяет доступность SQL. `docker compose logs --tail=100 app` показывает структурированные события запуска, ошибок обработки и доставки. Секреты и полный текст диктовки не выводятся в логи. При исчерпании пяти попыток outbox-сообщение остаётся в БД с `attempts=5`; исследуйте доступность бота и повторите доставку административно после устранения причины.

Пример диагностических запросов (в защищённой сессии DBA):

```sql
SELECT status, count(*) FROM reports GROUP BY status;
SELECT id, attempts FROM outbox WHERE NOT sent AND attempts >= 5;
```

Настройте внешние проверки health, дискового пространства, количества failed reports и неотправленных уведомлений. Масштабирование worker выполняйте только с обычным PostgreSQL. Встроенная БД — локальный режим.

## Резервное копирование

Python-скрипт использует стандартную библиотеку из `.venv` и команды Docker Compose. Он отказывается работать, если app запущен, чтобы SQL и вложения были согласованы.

```sh
docker compose stop app
.venv/bin/python scripts/backup.py backup --output backups/crm-2026-09-15.tar.gz
docker compose start app
```

Архив содержит SQL и файлы. Храните зашифрованную копию вне сервера с ограниченным доступом. Секреты `.env` в архив не попадают; храните их отдельно. Содержимое CRM требует согласованного срока хранения и доступов команды.

Восстановление выполняйте сначала в отдельной тестовой установке. Оно заменяет содержимое CRM-базы; нужен явный флаг:

```sh
docker compose stop app
.venv/bin/python scripts/backup.py restore --input backups/crm-2026-09-15.tar.gz --confirm-restore
docker compose start app
```

После восстановления проверьте health, число компаний, историю, вход менеджера и скачивание контрольного файла. SQL восстанавливается в одной транзакции. Если распаковка вложений завершилась ошибкой, оставьте app остановленным и повторите восстановление. Для Linux восстановите владельца `data/files` (UID 1000).

Для локального PGlite: остановите Node-процесс и копируйте весь `data/` вместе. Скрипт Docker-backup не предназначен для встроенного режима.

## Слияние

Проверки CI запускаются в feature-ветках и pull requests. Перед слиянием прочтите `docs/VERIFICATION.md` и ограничения интеграционных проверок. Защиту `main` (require PR + successful CI) следует включить в настройках GitHub репозитория; код сам не может обеспечить её включение.
