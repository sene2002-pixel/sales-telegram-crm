## Безопасность

Границы доверия проходят между оператором и proxy, клиентом Telegram и API, рабочим процессом и PostgreSQL, файловой системой, хранилищем копий и внешним ИИ. Источником роли служит активная запись пользователя. Короткие транзакции изменения CRM согласуют блокировки с действующей схемой: при необходимости сериализовать иерархию, затем операции изменения компаний, затем пользователь, компания и запись. Внешний сетевой вызов не должен держать эти блокировки. Копия должна быть приватной до записи содержимого, становиться видимой под окончательным именем только после успешной записи и сохранять уже существующий архив. Проверка лимитов проводится на малых тестовых значениях. Пороги для пользователей, хранение архивов и приёмка на стенде требуют отдельного решения.

### Раздельные роли PostgreSQL

Для новой отдельной БД администратор выполняет scripts/postgres-roles.sql. Скрипт создаёт две групповые роли без логина. Администратор выдаёт отдельному логину миграций право переключиться в crm_schema_owner, рабочему логину только crm_runtime. Для соединения миграций задаются DATABASE_URL с логином мигратора и PGOPTIONS="-c role=crm_schema_owner"; команда node dist/server/migrate.js создаёт объекты от роли владельца. Затем приложение запускается с APP_DATABASE_URL рабочего логина (вне Compose — DATABASE_URL), DATABASE_MIGRATE_ON_START=false, без параметров логина мигратора. Обычный логин должен иметь NOSUPERUSER, NOCREATEDB, NOCREATEROLE и не владеть схемой, базой и объектами. При плановом переводе существующей базы после проверенного бэкапа передайте владельцу схемы существующие объекты и явно выдайте рабочей роли DML-права на прикладные таблицы и USAGE на их последовательности. После выдачи прав отзовите у crm_runtime все привилегии на schema_migrations, как делает мигратор. ALTER DEFAULT PRIVILEGES в скрипте действует на будущие объекты. Для раздельного профиля укажите CRM_APP_ENV_FILE с переменными только рабочего приложения. Bootstrap-пароль и логин мигратора остаются вне этого файла. Подключение Compose без APP_DATABASE_URL сохраняет прежний профиль.

При откате приложения администратор сохраняет таблицы учёта и существующие архивы. Отключение AI_BUDGET_ENABLED и FILE_QUOTAS_ENABLED возвращает прежние ограничения. Физическое шифрование, срок хранения, фактические привилегии рабочего подключения и доступы к хранилищу подтверждает владелец целевой среды.

## Решения и приёмка

- Форма нового клиента, базовый тип холдинга, карточка клиента и общая отмена уже входили в main. Проверили исходные тесты и браузерные сценарии и закрыли четыре карточки в Asana.
- Для списка задач вернули действие завершения справа. Основная часть строки открывает детали, восстановление и отмена используют существующий механизм. Проверены мобильный и настольный размеры, клавиатура и поведение закрытых задач.
- Для формы холдинга владелец продукта подтвердил смысл верхнего ИНН. По нему подбирается или добавляется юрлицо, холдинг остаётся без ИНН. Сервер записывает изменения атомарно. Проверены смена категории, ошибка сети, конфликт версии, чужой ответственный и повтор.
- Фото таблицы с подписью /import передаётся существующему адаптеру ИИ. Распознавание заканчивается предпросмотром, подтверждать и отменять импорт может автор. Добавлены поиск Saby по имени и городу с проверкой ИНН и защита от неоднозначного выбора, сопоставление заголовков и форматирование телефонов с добавочным.
- Независимое ревью выявило потерю города или названия при ложном распознавании заголовка, местного телефона при определённом колонкой городе, несовпадение табличного TXT и CSV, перехват CSV с подписью /import. После исправлений отдельно проверены 39 сценариев и четыре сравнения исходных/полученных данных. Оба проверяющих просмотрели фактический diff на дублирование, неиспользуемый код и отладочные остатки.
- При повторной приёмке защиты проверены раздельные подключения PostgreSQL, отзыв права, сохранение согласованного снимка, резервирование файлов, контроль конкурирующих вызовов ИИ, общая очередь отчётов и писем, офлайн-сверка файлов и резервное восстановление на временных данных. Рабочие пороги остаются выключенными. Обоснование для их согласования приведено в [расчёте расходов](../../AI_COSTS.md).
- Живая проверка отправила одну синтетическую таблицу из двух строк. OpenAI вернул HTTP 403. Запрос метаданных модели подтвердил код unsupported_country_region_territory. Клиент получает предложение загрузить CSV/XLSX. В отдельном прогоне из работающего контейнера CRM на Windows версия распознавания для выпуска получила HTTP 200 от настроенной модели. У синтетической таблицы совпали все девять ячеек, включая порядок и ведущие нули. Проверка не записывала данные в рабочую базу. Доступ рабочего Saby ещё предстоит подтвердить.
- Проверенный локальный контейнерный прототип предпрода остановлен. Развёртывание постоянного стенда и изменение правил GitHub отложены владельцем; создана [отдельная задача](https://app.asana.com/1/1218599458205876/project/1218585786925552/task/1220662010440561).
