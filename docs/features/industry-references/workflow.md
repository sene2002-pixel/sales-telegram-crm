# Отраслевые референсы

## Требования и решения

Источник: согласованный пользователем документ «Правила-подбора-референсов-ESQ (1).md». Основная отрасль обязательна и подтверждается менеджером; AI не может переопределить её при генерации. Основные объекты имеют приоритет, смежный допустим один и только при нехватке двух основных. ★ и известность не разрешают выходить за отрасль. Один объект допускается, нейтральный абзац используется только при отсутствии объектов. Оборонные объекты требуют явного разрешения на упоминание.

Уточнение пользователя 07.10.2026: короткий абзац разрешён также для 2–3 объектов при недостатке фактов, для испытания с возможным последующим пересмотром. 330 знаков — целевая, а не обязательная нижняя граница. 420 знаков — максимум. Не дополняем факты и не пишем искусственный текст ради длины; разрешено раскрывать только сокращения из исходного словаря.

## Проектирование

- UX: проверка отрасли в текущей задаче Telegram, выбор/исправление из списка и повторное подтверждение. В CRM явный выбор отрасли перед генерацией. Неизвестная отрасль блокирует создание PDF.
- Каталог: индивидуальные стабильные ID, группы и факты из существующей базы; коммерческая/жилая недвижимость и оборонный сектор выделяются отдельно. Не добавляем неподтверждённых поставок.
- Генерация: только допустимые объекты передаются AI; структурированные ID проверяются сервером, фактический абзац собирается из доверенных записей, а не произвольных названий AI. Ограниченные повторы при недопустимом ответе. При сокращении сначала удаляем смежный объект, затем последний основной, сохраняя первый основной.
- Разнообразие: история ID успешно сохранённых писем текущего сотрудника; выбор других равноподходящих объектов, без снижения отраслевой точности и без передачи чужой истории.
- Security: прежние ACL/lease/повторное подтверждение сохраняются, источники и AI — недоверенные данные. Новая история содержит ID объектов, не персональные данные.

## Этапы

Analyst / Product / UX / Architect / Security: passed. Developer: passed. QA: passed — сборка приложения, полный прогон 320 тестов; после финального ограничения длины и проверки нейтрального сценария повторно прошли 13 профильных тестов. 7 ops-тестов и 2 Playwright-теста (desktop/mobile) прошли. Тестовый сервер проверяется через /api/health при запуске браузерных тестов. Внешние AI/Telegram ответы замоканы, живой бот не проверялся.

Независимое ревью: passed после исправления потери activity, обработки ДГУ/ДЭС и точных профилей, скобок регионов и сохранения предупреждения в подписи PDF. Исключение для коротких блоков согласовано пользователем. Product Owner: passed — фильтрация групп, ограничения смежных, повторное подтверждение, права/версии и фактический текст проверены. Release: ready locally, публикация и PR не запрошены.

В каталоге 176 индивидуальных объектов, 162 разрешены. Архив исходных формулировок сохранён, но не передаётся модели. Записи без подтверждённых фактов, запрещённые продукты/будущие проекты и оборонные объекты без разрешения исключены. Схема БД не меняется: история ID и предупреждений записывается в существующий audit атомарно с PDF.

## Проверки и откат

Проверить фильтрацию, лимит смежных, неизвестную отрасль, один/ноль объектов, запреты, разнообразие, сокращение, устаревшие/чужие кнопки, PDF и отсутствие регрессий. Изменения каталога и кода откатываются совместно; добавочная история может оставаться в БД. Перед production-обновлением резервная копия. Старые PDF не менять. Push/deploy только отдельным запросом.
