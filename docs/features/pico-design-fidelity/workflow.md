# Pico: точное соответствие экранов макетам

## Основание и границы

Пользователь запросил исправить все расхождения, выявленные повторной проверкой опубликованного изменения `670ddd6`. Источник — предоставленный PDF «Pico-макет-экраны», 6 страниц. MCP Asana отвечает HTTP 401, поэтому содержимое новой задачи не прочитано и не используется как выдуманный источник. Конфигурация MCP и локальные изменения `.gitignore`/`docs/ASANA_MCP.md` принадлежат другой работе и не изменяются этой задачей.

Первая реализация была принята по недостаточно строгому визуальному критерию. 60 E2E проверили выбранные сценарии, но не все элементы PDF. Повторная независимая проверка обнаружила пропущенные категории/направления/поставки/услуги, длинные старые формы, неверные цвета задач, отсутствие отдельной формы направления и экрана пользователей, неполный выбор периода и действия участников.

## Критерии

1. Мобильные контакты слева, потенциал и файлы справа, заметки на всю ширину; отдельная шторка направления, компактные суммы в млн ₽, поиск по контактам.
2. Компактные формы создания клиента/проекта/задачи; категории, направления, типы и роли как чипы; клиент и участник выбираются через поиск и список с иконками. Текст задачи доступен до выбора клиента и не теряется при его смене.
3. Восемь основных категорий клиента и семь направлений оборудования. Прежние ключи продолжают работать без фиктивного назначения напряжения старым ПЧ/УПП.
4. Проект сохраняет проектные поставки АСУ ТП/НКУ/ДГУ/другое и услуги шефмонтажа/ПНР/сервиса; неизвестные и смешанные суммы остаются null. Участники редактируются, удаляются и переставляются без потери данных.
5. Задачи имеют разные цветные значки, контекстную подсказку по подтверждённым данным, быстрый перенос с предпросмотром даты/времени и «Завтра утром» в 10:00.
6. Корона открывает компактный список «Пользователи» с ID, добавление только по ID; роли, блокировки и правило последнего администратора проверяются сервером.
7. Период аналитики выбирается радио-строками с диапазонами; отмена сохраняет прежний выбор, CTA на всю ширину. Квартал — завершённый календарный квартал, год — календарный год, неделя — текущая календарная неделя, месяц — 30 дней. Сравнение использует реальные исторические данные, а неизвестная база не превращается в +0%.
8. Два независимых тестировщика сравнивают все пустые/заполненные/вложенные состояния по снимкам на 390 px, проверяют 360 px/desktop, серверные негативные случаи и регрессии.

## Дизайн и безопасность

JSON-модели расширяются совместимо, схема SQL не меняется. `drives` остаётся отдельной исторической категорией «напряжение не указано», новые ключи — `drives_lv`/`drives_mv`; `hv_drives` в коммерческом регламенте тоже сохраняется. Категории вынесены в модуль без циклической зависимости sales/contracts. Низковольтные приводы сохраняют прежнюю vendor-логику ESQ; высоковольтным эта принадлежность не приписывается.

Поставки и услуги хранятся отдельными позициями equipment с собственными суммами. Редактирование не объединяет несколько старых позиций одного направления и не подменяет неизвестную сумму нулём.

`POST /users/admit` доступен только администратору, сериализует добавления и отвергает дубликаты, включая заблокированные и административные аккаунты. Новый доступ всегда manager; имя временно обозначается как `Telegram ID …` и заменяется только после доверенного входа из Telegram. Реальные Telegram/OpenAI вызовы и управление production не нужны. Старое управление пользователями сохраняет проверку последнего администратора.

`GET /tasks/:id/advice` проверяет доступ к компании и использует только подтверждённые nextStep/blocker либо подтверждённую договорённость. При неоднозначных проектах/предположениях показывается нейтральная инструкция, а не выдуманная рекомендация.

`GET /analytics` ограничивает данные текущими правами сотрудника. Исторические стадии и архив восстанавливаются из audit before/after. Новые company.created сохраняют исходный snapshot. Для старых карточек с недостаточной историей сравнение показывается недоступным. Существующие стадии CRM сохраняют собственные названия: «Предложение» и «Поставки» не переименовываются в факт отправки КП без основания.

## Проверки и откат

Серверные тесты: 6/6 новых независимых сценариев входят в `npm run check`: 331 passed, 2 skipped; 7 ops и build passed. Финальные UI-поправки повторно проверены обоими тестировщиками: 74/74 полного E2E; 14/14 визуальных сценариев desktop/mobile, 7/7 narrow, 2/2 affected после последней сборки. Визуальный аудит: 50 снимков (40 состояний плюс 360 px/desktop). Найденные обрезанный CTA задачи на 360×640, узкие CTA фильтров, слитая должность контакта, отсутствующий typebadge и ISO-дата вместо контекста проекта исправлены.

При откате старые strict-схемы не понимают новые ключи/позиции; перед согласованным выпуском нужна резервная копия. Сохранённые данные нельзя молча обрезать или переименовывать. Откат кода требует совместимой схемы чтения либо согласованного восстановления БД. В этой работе production-данные не изменяются.
