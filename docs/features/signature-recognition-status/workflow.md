# Статус распознавания визитки рядом с загрузкой

Источник — подтверждённый пункт локального UI-аудита 2026-11-01. Отдельная карточка Asana не создавалась.

## Требования и решение

При выборе фотографии статус обработки был только на нижней кнопке сохранения. Два аналитика подтвердили общий `busy` для сохранения и распознавания. Два дизайнера согласовали локальную строку под FileUpload: «Распознаём визитку…», затем предложение проверить и сохранить данные, либо ошибка. Статус 13/18, отступ 8 px, мягкий синий фон; ошибка использует существующую палитру. Оценка частоты пользовательских ошибок не проводилась.

Критерии: feedback рядом с фото, доступный live status/alert; повторный выбор сбрасывает прежний результат; ошибочный/слишком большой файл не очищает введённые поля; распознавание не сохраняет подпись автоматически; сохранение не объявляется распознаванием. Оба сценария использования SignatureEditor (профиль/письмо) остаются совместимыми.

Небольшое UI-исправление. Общий FileUpload, API, ACL, хранение, распознавание на сервере и голосовые черновики не меняются. Синхронный guard исключает пересечение операций в одной форме. Миграции не нужны, откат — revert PR.

## Этапы

- Анализ двумя аналитиками: passed.
- UX/дизайн до кода двумя дизайнерами: passed.
- Разработка: passed. Статусы и ошибки фото локальны в SignatureEditor; `useId` связывает feedback с input, постоянно смонтированный `role=status` объявляет обновления, ошибки используют `role=alert`. Синхронный guard блокирует пересечение операций.
- Два ревью фактического diff перед QA: passed (`keyboard_code_review`, `swipe_code_review_2`), блокеров нет.
- Визуальная приёмка: passed, итерация 1. Оба дизайнера лично открыли по пять реальных кадров pending/error/success на 320/390/1440 через `view_image`. Изменений после приёмки не потребовалось.
- QA: passed на Node 22.23.4 (ветка Node 22, как в CI). `npm run check`: 514 passed, 4 штатных skipped, 7 ops, build. Playwright: 12 desktop + 12 mobile passed (`signature-recognition-status`, `letters`, `ui-audit-visual`). `/api/health` проверяется при запуске локального браузерного сервера.
- Приёмка: passed. Pending/error/success видны возле uploader без прокрутки к Save; четыре сценария ошибки/повтора/размера/сохранения проверяют отсутствие автосохранения, сохранность полей и сброс устаревшего статуса. Запрос сохранения во время распознавания блокируется. Существующий сценарий письма проверен настоящим локальным API сохранения.
- CI и выпуск: pending, слияние только после зелёных проверок PR.

Окружение: первоначальный `npm run check` на системном Node 26.7.0 дал 513 passed/1 failed (существующий HTTP rate-limit: 404 вместо 400); изолированный повтор дал 401 вместо 200. На Node 24.19.0 отдельный тест прошёл, полный прогон завис в существующем наборе ролей и был остановлен. Перепланировали проверку на Node 22, совпадающий с CI; полный набор прошёл без изменения серверного кода или ослабления тестов. Точная причина нестабильности других runtime не установлена.

Кадры воспроизводятся новой спецификацией: `/tmp/signature-status-{pending,error,success}-{320,390,1440}-{desktop,mobile}.png`. Браузерные проверки используют синтетический ответ распознавания; фактическая точность OCR не входит в UI-исправление. Mobile — Chromium touch, физические устройства не проверялись. Предупреждение Vite о размере bundle существовало ранее.
