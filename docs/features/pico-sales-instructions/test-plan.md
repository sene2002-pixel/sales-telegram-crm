# Матрица проверок

| Критерий                          | Проверка                                                                                                                                                                                      |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Единый строгий контракт        | SALES-01: схема, nullable/default, запрет неизвестных полей и неверных дат; SALES-09: обработка диалога и подтверждение.                                                                      |
| 2. Шесть подтверждённых признаков | SALES-02: совместный балл контакта/доступа, false и assumptions; SALES-07: известные сведения.                                                                                                |
| 3. Политика вопросов              | SALES-03: границы сумм, отложенный ввод, открепление, неперспективность; SALES-07: отсутствие повторов; SALES-09: общий бюджет.                                                               |
| 4. История и разделение проектов  | SALES-04: null/assumptions/false; SALES-05: идентичность и неоднозначность; SALES-06: ограничение вендоров; SALES-08: idempotency и датированные ревизии; SALES-10: привязка договорённостей. |
| 5. Коммерческий отчёт и ACL       | SALES-08: manager forbidden, лидер, период и статус; SALES-11: неоднозначные проекты, результат отдельно от объёма сделки.                                                                    |
| 6. Mini App                       | `e2e/sales.spec.ts`: пять блоков, история, оценка и коммерческий отчёт на desktop/mobile.                                                                                                     |

Команды: `npm run check`, `npx tsx --test src/tests/sales.test.ts`, `npm run build`, `npm run test:e2e`. Не отключать проверки авторизации или лимиты запросов ради зелёных тестов. Исправленный UI-06 использует менеджера, действительно закреплённого за тестовым руководителем; тестовые сессии повторно используются, чтобы не исчерпывать действующий auth rate limit.

Перед выпуском дополнительно проверить настоящий голос Telegram и ответ модели, исправление черновика, повторное подтверждение, отчёт руководителя и отказ менеджеру. Внешние вызовы требуют тестовых ключей и отдельного разрешения на изменение живого бота.
