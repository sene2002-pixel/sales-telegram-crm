# Холдинги и создание клиентов

POST /companies принимает обычные поля компании и необязательный initialContacts (до 20 контактов). Компания и контакты сохраняются одной транзакцией, источник контакта — user. website допускает пустое значение либо http(s) URL без логина и пароля. Старый внутренний create() по-прежнему принимает только поля компании.

holdingId — необязательный UUID или null. Связь разрешена только заказчику с неархивным холдингом того же ответственного, доступным пользователю. У холдинга нет ИНН или собственного родителя. Перед архивированием связанной компании, изменением типа холдинга или переназначением необходимо убрать связи. Проверки выполняются сервером под блокировками.

GET /companies/:id дополнительно возвращает holdingMembers, holdingPotential и holdingDivisions. Сумма включает только видимых неархивных дочерних заказчиков и не изменяет сохранённый собственный потенциал холдинга. Сохранённый временный потенциал не распределяется автоматически: распределение выполняется отдельным явным подтверждённым действием allocateHolding с версиями всех участников.

Холдинг поддерживает контакты и задачи. Проекты, участие в проектах и коммерческие отчёты должны относиться к заказчику. Старые категории остаются допустимыми для совместимости; новый список выбора использует восемь актуальных категорий. Шкафы АСУ ТП — самостоятельное направление automation_cabinets.

Общая аналитика исключает собственный потенциал холдинга, если у него есть доступные пользователю неархивные заказчики. Холдинг без таких заказчиков учитывает свой временный потенциал. Для анализа приростов правило проверяется на дату события. Невидимые дочерние компании не влияют на доступную пользователю сумму.

## Подтверждённый общий справочник

`shared/holding-catalog.ts` используется созданием клиентов, диалогом и подбором референсов. В нём группы из исходной инструкции и подтверждённые связи: ТГК-1 → ПАО «ТГК-1», ООО «ГЭХ-Закупки»; РМК → Кыштымский МЭЗ, Михеевский ГОК, Карабашмедь. Справочник также включает точные юридические имена и принадлежность из согласованного assets/esq/REFERENCES_ESQ.md: объекты СИБУР, Амур Минералс (РМК), ЭН+ Торговый дом (РУСАЛ), НЛМК-Урал и АО «ТГК-1». Иные связи не достраиваются моделью. Название группы без юрлица означает холдинг без ИНН; юридическое наименование означает заказчика. Явный ручной holdingId имеет приоритет. Группа и явно названное юрлицо создаются/связываются в одной транзакции у одного ответственного; существующий холдинг переиспользуется. При отборе референсов два объекта одной подтверждённой группы не допускаются в одном письме.

ТЭЦ/филиал/цех/площадка сохраняется в sites явно названного владельца. Для явно указанного владельца допустим разделитель запятая, двоеточие или тире. Если известна только группа, площадка временно хранится в группе; без владельца сервер требует уточнение и не создаёт отдельную компанию. Одно неизвестное справочнику юрлицо с филиалами не получает вымышленного родителя. Нет поиска ИНН по имени группы.

Появление заказчиков не удаляет временную оценку холдинга. `holdingAllocationRequired` в detail показывает необходимость явного распределения. `allocateHolding` проверяет актуальные версии всех участников, точные суммы по группам и права; только после подтверждения обнуляет временную оценку родителя. Произвольного автоматического деления нет.

## Атомарный редактор

`updateWithContacts` принимает `{version,data,contacts:[{id?,version?,data}]}`. Для существующего контакта обязательны id+version; он должен принадлежать редактируемой компании. Компания и контакты проверяются и изменяются одной транзакцией. Конфликт любой версии откатывает всё. После получения транзакционной блокировки сервер заново читает и блокирует действующего пользователя; деактивация и изменение роли не обходятся старым HTTP-снимком. Невидимое в форме поле добавочного номера сохраняется при его отсутствии в запросе. Пропущенные контакты не удаляются; удаление — отдельное явное действие. ИНН уникален в рамках ответственного, включая архив; у разных ответственных одинаковый ИНН разрешён. Переназначение на ответственного с таким ИНН возвращает409 без частичного переноса.

При непустой детализации оборудования явно заданный общий потенциал холдинга должен совпадать с её суммой (точность копейки). Противоречивый новый запрос отклоняется с объяснением; сервер не выбирает произвольно, какую подтверждённую оценку потерять. Старые данные не переписываются миграцией: противоречие требует явного исправления перед новым сохранением. Существующие каталожные алиасы распознаются при повторном создании группы у того же ответственного. При этом явно заданный ИНН всегда определяет юридическое лицо: совпадение названия не переносит контакты на карточку с другим ИНН.

В коротких транзакциях диалога используется порядок блокировок company-write advisory → текущий пользователь → данные действия/компания; модель вызывается вне транзакции. Это согласует диалог с новым атомарным редактором. Нативную конкурентную проверку PostgreSQL необходимо отличать от адресного PGlite-теста порядка запросов.
