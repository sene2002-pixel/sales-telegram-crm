# Возможности Telegram CRM и критерии готовности

Документ описывает реализуемую первую версию. Одна установка обслуживает одну команду. Интерфейс и сообщения — на русском языке. Исходный `app.jsx` сохраняется как дизайн-прототип; рабочее приложение находится в `src/web`.

## 1. Основа и окружение

- Отдельная ветка `feat/telegram-crm-platform`; изменения попадают в `main` только через pull request.
- TypeScript, React Mini App и NestJS API. Локальные npm-зависимости, отдельное Python-окружение `.venv` для эксплуатационных инструментов.
- PostgreSQL в production; встроенный PostgreSQL PGlite с записью на диск для локальной разработки без Docker. Общие SQL-миграции и бизнес-сервисы.
- Версионированная схема БД, проверка конфигурации при старте, переменные окружения без секретов в Git.
- Постоянное хранение компаний, контактов, проектов, задач, взаимодействий, отчётов, сотрудников, файлов и аудита.

Критерий: после перезапуска API созданные записи остаются доступными. Production не запускается с демонстрационной авторизацией или без обязательных секретов.

## 2. Доступ и сотрудники

- Вход из Telegram Mini App: серверная проверка HMAC-подписи `initData`, возраста и будущей даты авторизации; ограниченная по времени подписанная сессия.
- Bootstrap администратора по заранее настроенному числовому Telegram ID. Остальных сотрудников администратор добавляет по ID; произвольный пользователь не получает доступ.
- Роли `manager`, `supervisor`, `admin`. Менеджер работает только с закреплёнными компаниями и собственными отчётами. Руководитель видит общую CRM, отчёты и перераспределяет компании. Администратор дополнительно управляет сотрудниками.
- Блокировка сотрудника отзывает доступ при следующем API-запросе, даже если сессия ещё действует. Защита последнего активного администратора.
- Локальный демонстрационный вход доступен только при явно включённом DEV_AUTH вне production и только с loopback-запросов.

Критерий: подмена ID записи не позволяет менеджеру читать/менять чужую компанию, контакт, задачу, проект, файл или аудит.

## 3. CRM и справочники

- Компании: название, ИНН с контрольной суммой, город, сегмент, отрасль, стадия, статус архива, ответственный, оборот, потенциал, заметки, потенциал по направлениям.
- Сегменты: щитовик, OEM, конечный заказчик, подрядчик. Направления: 0,4 кВ, 6–35 кВ, ПЧ/УПП, КСО/КРУ, теплотехника, услуги.
- Поиск по названию/ИНН, фильтры по городу, сегменту, направлению, ответственному и архиву. Ответственный виден на карточке.
- Уникальный ИНН при наличии. Одно название не является основанием автоматически перезаписывать организацию.
- Контакты: имя, должность, телефон, email; привязка к компании; создание и редактирование.
- Проекты: компания, название, сумма, срок, статус, описание. Список и редактирование.
- Задачи: компания, необязательный проект, текст, срок, ответственный, состояние выполнения и фактическое время завершения. Список, фильтры, создание, редактирование и календарь.
- История общения: записи о звонках/встречах/договорённостях, автор, дата и источник. История отделена от текущих заметок компании.
- Файлы: загрузка до 10 МБ, защищённое скачивание, компания и необязательный проект, категория; удаление из интерфейса через архивирование метаданных. Физические файлы хранятся в постоянном томе.
- Защита от перезаписи устаревшей карточки посредством версии записи.

Критерий: все операции сохраняются на сервере и доступны после повторного входа; конкурирующее редактирование возвращает конфликт, а не затирает данные.

## 4. Бот и голосовые отчёты

- Личный чат: `/start`, `/help`, `/crm`, `/tasks`; кнопка CRM в меню бота. Команда возвращает кнопку Mini App, открытие происходит нажатием пользователя.
- Голосовое сообщение до настроенных лимитов длительности/размера или текстовый отчёт. Групповые сообщения не используются для ввода CRM.
- Проверка секретного заголовка webhook; повторная доставка update не создаёт повторный отчёт.
- Durable inbox/очередь в PostgreSQL: приём и постановка в одной транзакции, отдельная фоновая обработка, lease и повторные попытки с задержкой, восстановление после перезапуска.
- Скачивание Telegram-аудио с ограничением размера. Адаптер транскрипции OpenAI; модель задаётся конфигурацией.
- Структурирование через JSON Schema: одна или несколько компаний, контакты, задачи, дата взаимодействия, описание, потенциал и направления.
- Никакого исполнения инструкций из диктовки: это исходные данные. ИИ не определяет права доступа и ID ответственного.
- При неизвестных значениях используются null/пустые списки; неоднозначные даты и названия сопровождаются предупреждением. Даты интерпретируются относительно времени сообщения и часового пояса команды.
- Поиск доступных компаний по ИНН или точному имени. Несколько совпадений требуют явного выбора; неизвестная организация может быть создана по подтверждению.
- Черновик в боте: краткая сводка, сохранить, исправить в Mini App, отменить. Mini App позволяет корректировать поля и выбирать компанию.
- Сохранение всех блоков транзакционно. Повторное подтверждение не создаёт новые задачи или контакты. Сохраняются исходный текст, транскрипция, автор, время, предупреждения и связи с созданными записями.
- Состояния: queued → processing → review → saved/cancelled; после исчерпания попыток failed; ручной повтор failed.
- Нет ключа ИИ — обработка сообщает о конфигурационной ошибке, а не выдаёт выдуманный результат. Ручное ведение CRM продолжает работать.

Критерий: голосовое → черновик → подтверждение → записи в компании и календаре; рестарт и повтор webhook/подтверждения не дублируют результат.

## 5. Руководитель

- Общая панель: компании, открытые/просроченные/завершённые задачи, взаимодействия за выбранный период, компании без контакта последние 14 дней.
- Разбивка по сотрудникам; фильтр периода. Показатели работы считаются по автору взаимодействия/исполнителю задачи, владение компаниями — по текущему ответственному.
- Передача компании другому активному сотруднику. Открытые задачи передаются вместе с компанией; авторы прошлых отчётов и выполненных задач сохраняются.
- История назначений: кто передал, кому, когда; аудит создания, изменения, архивации, подтверждения отчёта и управления доступом.
- Доступная руководителю выгрузка сводки в CSV с защитой от формул электронных таблиц.

## 6. Эксплуатация и проверка

- Health/readiness endpoint, ограничения запросов и загрузок, таймауты внешних сервисов, безопасные сообщения об ошибках, структурированные диагностические логи без токенов и диктовок.
- Dockerfile и Compose с PostgreSQL, постоянными томами, healthcheck; HTTPS обеспечивается внешним reverse proxy по инструкции.
- Скрипт настройки webhook и меню бота запускается отдельно, только после настройки HTTPS и токенов.
- Инструмент резервного копирования и восстановления PostgreSQL + каталога вложений, процедура проверки восстановления. Встроенную dev-БД копируют только при остановленном приложении.
- Автоматические проверки бизнес-правил, авторизации, изоляции сотрудников, транзакций отчётов, идемпотентности, очереди и сборки; CI для pull request.

## Границы первой версии

Внешний платный справочник по ИНН, телефония, почтовая рассылка, несколько организаций в одной установке, SSO, распознавание телефонных звонков и автоматическая оценка качества сотрудников не входят в эту версию. Неопределённые ИИ-изменения требуют подтверждения. Проверка реального Telegram/OpenAI и публичного HTTPS требует рабочих пользовательских реквизитов; локальные тестовые адаптеры не считаются проверкой внешнего сервиса.
