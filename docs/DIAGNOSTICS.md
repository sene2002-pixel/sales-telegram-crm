# Временная подробная диагностика

Для разбора голосовых запросов и генерации писем есть отдельная таблица `diagnostic_logs`. Она создаётся при запуске обновлённого приложения. Нового раздела в Mini App нет. Диагностические события записываются **только в БД**, без копирования в Telegram или логи Docker. Обычный журнал ошибок `error_logs` работает независимо.

## Включение на Windows / Docker

По умолчанию подробная диагностика выключена. Чтобы включить её на сутки, получите конечное время в PowerShell:

```powershell
(Get-Date).ToUniversalTime().AddHours(24).ToString("yyyy-MM-ddTHH:mm:ssZ")
```

Вставьте полученное значение в `.env` после `DIAGNOSTIC_LOG_UNTIL=`. Не добавляйте эту настройку несколько раз. Затем пересоздайте приложение:

```powershell
docker compose up -d --build app
```

Повторите проблемный запрос боту. Ранее произошедшие события задним числом не появятся. После указанного времени запись новых подробных событий остановится автоматически, без перезапуска. Для досрочного отключения очистите значение `DIAGNOSTIC_LOG_UNTIL` и повторите команду выше. Неверный формат даты останавливает запуск с понятной ошибкой; требуется ISO-дата с часовым поясом.

## Что записывается

- Время события в БД, сотрудник (`actor_id`), общий идентификатор цепочки (`trace_id`), ID отчёта/задачи и номер попытки.
- Приём сообщения Telegram, тип сообщения, распознанный запрос и выбор сценария: письмо, подпись, создание контакта, отчёт или неизвестная команда.
- Загрузка голосового, распознавание, извлечение отчёта, постановка в очередь, выбор подписи и отмена.
- Начало и результат поиска компании; используемая модель, типы действий поиска, поисковые запросы, HTTP-статус, ID ответа и `x-request-id` сервиса ИИ. Фиксируются длительности запросов, без HTTP-заголовков и полного тела ответа.
- В `letter.sources.checked`: ссылки, наблюдавшиеся в поиске (`observed`), ссылки модели (`claimed`), несовпавшие ссылки (`unmatched`), их нормализованные варианты и итог проверки (`matched`, `missing`). Это позволяет отличить отсутствие источников от несовпадения URL.
- Поиск/создание компании в CRM, подбор референсов, рендер PDF, сохранение файла и контакта, доставка PDF в Telegram, повторная попытка или окончательный отказ.
- Постановка уведомлений в outbox и их доставка. Их `trace_id` сохраняется между запросом и фоновой отправкой.
- HTTP-запросы приложения: начало, завершение, шаблон маршрута, статус, сотрудник после авторизации и длительность. Параметры URL, тела запросов и токены скачивания не записываются.

Цепочка Telegram имеет вид `telegram:<update_id>` и сохраняется при автоматических повторах. HTTP-цепочка — `http:<X-Request-ID>`. События запуска имеют `trace_id=system`. До авторизации сотрудник может быть ещё не определён; в событии Telegram есть числовой ID отправителя.

Идентификаторы HTTP-запросов к ИИ добавлены с учётом [рекомендаций OpenAI по диагностике API](https://developers.openai.com/api/reference/ruby).

## Как посмотреть

Последние события, начиная с новых:

```powershell
docker compose exec postgres psql -U crm -d crm -x -c "SELECT created_at, trace_id, actor_id, entity_id, attempt, event, details FROM diagnostic_logs ORDER BY seq DESC LIMIT 50;"
```

Вся цепочка последнего запроса письма, в порядке выполнения:

```powershell
docker compose exec postgres psql -U crm -d crm -x -c "SELECT d.created_at, d.trace_id, u.name AS employee, d.entity_id, d.attempt, d.event, d.details FROM diagnostic_logs d LEFT JOIN users u ON u.id=d.actor_id WHERE d.trace_id=(SELECT source_key FROM letter_jobs ORDER BY created_at DESC LIMIT 1) ORDER BY d.seq;"
```

Если запрос не дошёл до очереди писем, возьмите `trace_id` из последних событий `telegram.received` и используйте его в фильтре:

```sql
SELECT created_at, actor_id, entity_id, attempt, event, details
FROM diagnostic_logs
WHERE trace_id = 'telegram:123456'
ORDER BY seq;
```

`seq` задаёт порядок записи; он может иметь пропуски после отката транзакций. События внутри транзакции сохраняются вместе с её успешными изменениями. При отказе ищите итоговые `*.failed`, `letter.enqueue.rejected` или `letter.voice.rejected`, записанные после отката.

## Хранение и ограничения

- Срок хранения — **три календарных месяца**. Очистка обоих журналов выполняется при запуске и затем каждый час, даже если обработчики фоновых задач отключены. Выключение диагностики не удаляет уже накопленные записи. Резервные копии имеют собственный срок хранения.
- Полный аудиофайл, PDF, содержимое подписи, исходный ответ ИИ, HTTP-заголовки и известные секреты конфигурации не сохраняются. Для распознанных команд подписи и создания контакта вместо текста пишутся тип сценария и длина (для подписи — также операция). Обычные запросы/отчёты содержат рабочую информацию и могут содержать персональные данные: доступ к БД должен быть ограничен.
- Дополнительно маскируются явные email, телефоны с `+`, токены и пароли. Это не универсальный детектор любых персональных данных в свободном тексте. Значения query-параметров источников заменяются короткими SHA-256 отпечатками для сравнения, credentials и фрагменты ссылок скрываются. Путь и домен источника остаются для диагностики.
- Размер одной записи ограничен 32 КБ UTF-8; длинные строки, коллекции и вложенность обрезаются. В очень большом событии будет `truncated=true`.
- Ошибка диагностической записи не должна прерывать бизнес-операцию; внутри транзакции используется savepoint. Если БД недоступна, диагностика теряется и не переносится в stdout/stderr. Общее поведение обычного `error_logs` при сбое БД описано отдельно в `ERROR_LOGS.md`.
- Это трассировка выполнения приложения, не журнал каждого SQL-запроса, ОС, Docker или браузера. Подробный режим увеличивает число записей в БД; включайте его на время воспроизведения, а не постоянно.
- Инструментирование не отключает проверку источников и само по себе не исправляет сбой поисковой выдачи. Для определения причины нужны записи нового запроса с проблемного сервера.
