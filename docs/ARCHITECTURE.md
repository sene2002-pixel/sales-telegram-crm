# Архитектура

## Границы модулей

Модульный монолит: один deployable NestJS API и статическое React-приложение, один SQL-store. HTTP-контроллеры проверяют транспортные схемы и передают сценарии сервисам; Telegram — альтернативный вход к тем же сервисам. `Services` является composition root: явно собирает зависимости и передаётся NestJS через DI. По мере роста доменные области можно разделить на Nest-модули без изменения сервисных контрактов.

`AuthService`: Telegram-подпись, сессии, сотрудники. `CrmService`: компании, назначения и связанные записи. `ReportService`: inbox, черновики, транзакционное применение. `ReportWorker`: состояния, leases и retries. `BotService`: команды и callbacks. `DashboardService`: агрегаты и CSV.

`Database` реализует контракт `Sql` поверх pg/PGlite и транзакций. Репозиторий использует параметризованный SQL, а не конкатенацию пользовательских значений. `SpeechToText`, `ReportExtractor`, `Messenger` — интерфейсы внешних адаптеров; они заменяются в тестах. Бизнес-сервисы не зависят от HTTP-контроллеров.

## Модель данных

`users` → `companies.owner_id`; `companies` → `records.company_id`. В `records` хранятся типизированные схемами contact/project/task/activity/file. Общие обязательные отношения имеют внешние ключи, вариативные поля — JSONB. Это сознательный компромисс первой версии: меньше повторяющегося CRUD, но тип записи и его схема проверяются на сервере. При росте объёмов task/activity можно выделить в отдельные таблицы без изменения публичного API.

`records.author_id` не меняется при передаче компании. `assignee_id` используется для задач: открытые передаются новому владельцу, выполненные сохраняют исполнителя. `reports.author_id` принадлежит реальному отправителю. Подтверждение руководителем сохраняет исходного автора взаимодействия и отдельно фиксирует подтверждающего в аудите.

Денежные поля API задаются в рублях. UI явно указывает единицы; исходный прототип хранил часть величин в миллионах и не является форматом миграции данных. Импорт исторических данных потребует отдельной процедуры преобразования.

## Конкурентность и очередь

1. Уникальный `reports.source_key` предотвращает дубли входящих Telegram updates / повторов веб-запроса.
2. Состояние `queued` само является надёжной очередью: запись не зависит от доступности отдельного брокера.
3. Worker атомарно забирает запись через `FOR UPDATE SKIP LOCKED`, устанавливает lease на четыре минуты и случайный fencing token.
4. Внешние вызовы ограничены таймаутами. Просроченный lease возвращает запись в обработку; старый worker не может записать результат после смены token.
5. Ошибки временной недоступности повторяются до трёх попыток с задержкой. Ошибки входных данных/конфигурации сразу видны пользователю.
6. Подтверждение блокирует report и компании, применяет все изменения одной транзакцией, записывает аудит и outbox. Повторный вызов возвращает прежний результат.
7. Outbox доставляет уведомления с повторами. Доставка Telegram at-least-once: при сбое после отправки и до commit уведомление может повториться; CRM-записи при этом не дублируются.

Версии компаний, записей и черновиков защищают от stale edits. ИНН уникален при наличии. Нечёткий поиск не используется для автоматической перезаписи компаний.

## Доступ и защита

На каждой операции проверяется активность пользователя, роль и владение компанией. Скрытые кнопки не являются механизмом безопасности. Сессия подписана HMAC, срок восемь часов; авторизация Telegram принимает данные не старше часа. Токен сессии хранится в sessionStorage и передаётся в Authorization.

Загружаемые файлы получают случайные имена. Публичной папки вложений нет. Скачивание только после ACL, как attachment с octet-stream. Удаление — архивирование метаданных; очистка физического хранилища выполняется отдельно по политике хранения.

ИИ видит текст диктовки и контекст даты, но не получает доступ к SQL или выбору полномочий. Выход проходит Zod-валидацию и подтверждение человеком. Проверка схемы не гарантирует фактическую точность — подтверждение сохраняется как часть продукта.

## Ограничения масштаба

Первая версия рассчитана на небольшую команду: списки компаний/задач и агрегаты сейчас загружаются целиком, отчёты ограничены последними 200, аудит карточки — 100 событиями. Для десятков тысяч записей нужны серверная пагинация, индексы на JSONB и SQL-агрегаты. In-memory rate limits действуют в пределах одного процесса; при нескольких репликах ограничение следует перенести на gateway/Redis. PGlite допускает только один процесс-владелец; production использует PostgreSQL.
