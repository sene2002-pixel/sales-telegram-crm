# HTTP API и Swagger UI

Исходник спецификации — `src/server/http/openapi-document.ts`, необязательный экспорт OpenAPI 3.1 — `docs/api/openapi.json` (не хранится в Git). Входные схемы извлекаются из действующих Zod-валидаторов с `io: input`; описания дополняют проверки ИНН, календарных дат, состояния, версий и доступа. Сервер остаётся источником прав. Восьмибалльная воронка клиента описана отдельно от ручных стадий и шести пунктов сделки.

Спецификация охватывает 55 явных HTTP-операции контроллеров: 7 публичных/специально защищённых и 48 с bearer-сессией. Публичные download URLs требуют краткоживущий opaque token; webhook требует свой заголовок секрета. Внутренние Telegram callbacks и фоновые операции не представлены как новые HTTP endpoints.

## Доступ к документации

После `npm run build` и `npm start` Swagger доступен по `/api/docs` (локально обычно `http://localhost:3000/api/docs`). Сборка сама по себе не запускает HTTP-сервер. Документация включена по умолчанию; `API_DOCS_ENABLED=false` явно отключает её и возвращает 404 для всех её маршрутов. Если в существующем `.env` стоит `false`, замените на `true` и перезапустите приложение. `/api/docs` показывает форму входа. Она и локальные JS/CSS доступны без сессии, но не содержат схему, список прикладных маршрутов или конфигурацию сервера.

Администратор вводит токен собственной текущей Pico-сессии. Форма очищается сразу; токен используется только в памяти для запроса `/api/docs/openapi.json` через `Authorization: Bearer …`. Схема доступна только после новой проверки активной роли admin в БД. Токены в query string, cookies, localStorage или sessionStorage документация не использует. Нельзя передавать токены, Telegram initData и ссылки скачивания третьим лицам или сохранять их в примеры/скриншоты.

Swagger UI служит справочником: выполнение запросов (`supportedSubmitMethods: []`), сохранение авторизации, настройка через URL и внешний валидатор отключены. Это не замена серверной авторизации. Уже прочитанную/скачанную администратором спецификацию невозможно отозвать из его памяти браузера; новые обращения после отзыва прав запрещаются.

Используется локальный `swagger-ui-dist` 5.33.2, Apache-2.0. CDN не требуется. У пакета есть зависимость `@scarf/scarf` 1.4.0; `scarfSettings.enabled=false` в package.json отключает её install telemetry. Первичная установка выполнена с `--ignore-scripts` и `SCARF_ANALYTICS=false`. Рекомендуется сохранять этот opt-out и при CI-установках. Политика CSP для страниц документации не разрешает inline scripts, eval или сторонние источники.

## Обновление

После изменения маршрута или схемы:

```sh
npm run build:server
node --test dist/tests/openapi.test.js
```

Сервер формирует спецификацию непосредственно из TypeScript и не читает JSON-файл. Для экспорта в Postman или другие инструменты выполните `npm run api:export`: команда создаст игнорируемый Git файл `docs/api/openapi.json`. Экспорт не нужен для сборки, запуска или Swagger. Генератор не читает окружение, БД или реальные запросы; JSON не копируется в публичный `dist/web`. Тесты проверяют соответствие всем текущим декораторам маршрутов, ссылки компонентов, соответствие экспорта схеме в памяти и неизменяемые серверные поля. Проверка актуальности сравнивает разобранную структуру JSON: отступы и порядок ключей разрешены, изменение содержимого или удаление маршрута отклоняется. Для Swagger UI используется базовый диалект OpenAPI 3.1, расширяющий JSON Schema 2020-12.

Примеры синтетические. Схемы не обещают наличия внешних сервисов: распознавание и PDF требуют своей конфигурации, Telegram-отправка — действующего бота и числового Telegram ID. Нельзя проверять такие операции в production без отдельного разрешения.

## Ограничения описания

Некоторые бизнес-проверки нельзя выразить одним JSON Schema: контрольная сумма ИНН, доступ к выбранной компании, соответствие `kind` конкретной схеме `data`, исторические связи и актуальная версия. Они описаны у операций и исполняются сервером. Служебный глобальный порядок аудита не является публичным DTO.

Откат документации: выключить `API_DOCS_ENABLED` и развернуть предыдущий код; миграции БД и изменение прикладных данных этой функцией не требуются.

## Приглашения в команду

- `GET /api/team-invitations`: метаданные приглашений; руководителю только свои в своей команде, администратору все. Без исходных ссылок.
- `POST /api/team-invitations`: руководитель отправляет `{}`, администратор `{ "supervisorId": "UUID активного руководителя" }`. Возвращает ссылку только один раз. Срок24часа, новый участник получает manager; нельзя передать role или чужую команду от руководителя.
- `POST /api/team-invitations/:id/revoke`: отзыв неиспользованного приглашения. Не удаляет уже принятого сотрудника.

Сотрудник открывает ссылку и нажимает Start в личном Telegram-чате. Погашение выполняется webhook по доверенному sender, а не по Telegram ID из браузера. Уже добавленный или заблокированный пользователь не переводится и не получает новые права. Ссылку передавайте лично: её первый получатель может занять приглашение. Не публикуйте её в общих чатах. Для работы требуется действующий BOT_TOKEN и настроенный webhook; адрес ngrok не является частью пригласительной ссылки.

## Закрытые задачи и редактирование связей

`PATCH /api/records/:id` сохраняет прежнюю проверку версии и прав на компанию. Только для задачи дополнительно разрешены необязательные `projectId` и `assigneeId` (UUID или null): проект должен принадлежать этой же компании; новый ответственный должен быть активным и доступным через существующие правила команды, а также уже иметь право читать компанию: быть её менеджером-владельцем либо руководителем/администратором. Назначение на другого менеджера той же команды не даёт ему доступ к чужой компании и поэтому запрещено. Неизменённый исторический ответственный может сохраняться. Компания задачи этим маршрутом не меняется. Управление пользователями и назначение ответственного сериализуются общим lock, поэтому отзыв доступа не обходится устаревшим списком UI.

Удаление из шторки задачи использует `data.deleted=true` и `done=true` через этот PATCH, сохраняя запись в «Закрытых». `completedAt` в этом состоянии сервер обнуляет; удалённые задачи не дают баллы и не учитываются как выполненные за период. Старые задачи без `deleted` сохраняют прежнее поведение. Пропущенный флаг при обновлении сохраняется. Удалённую задачу сначала явно возвращают в работу (`deleted=false`, `done=false`, остальные данные без изменений), после чего её можно редактировать. Старый `DELETE /api/tasks/:id` сохраняет прежнюю семантику и не используется новой шторкой.

Трёхсекундное «Отменить» — клиентское окно до отправки PATCH, а не обратный запрос после изменения. Переключение вкладки не теряет очередь; выход, смена сессии или сотрудника отменяют неотправленные действия. После начала запроса отмена недоступна; ошибки показываются без автоматического повторения от имени другой сессии.
